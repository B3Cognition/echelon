# Following integration observations — not additional current-task requirements

- Source-context acceptance is not the immutable managed-run registry. A live owner must independently bind workspace/epoch, canonical spec, exact run/source context and enabled feature contract. Removing a feature field must not silently downgrade a spec already registered as managed. No registry schema/API selected in this note.
- `SquadController._prepare_controller_completion` calls `prepare_controller_completion_stage` with publication/route/effects and judgment payload hashes. `squad_completion._validate_publication` currently accepts exactly kind:none or kind:external plus its marker, with closed intent/receipt validation. Source journal request version2 does not automatically extend or authenticate this completion format; real owner composition and recovery must be explicit.
- `_prepare_controller_completion` uses the current run-local spec path for checkpoints and seals effects before state advancement. Terminal and resolution origins have distinct effect plans. `_publish_and_finalize` handles external publication separately. Managed identity enforcement must cover ordinary/manual run-local authoring as well as final external export, without allocating/applying a second revision solely for export.
- `PhaseExecutor._phase_prompt_metadata` currently attaches exclusive write paths only to SAGE phase1-why2 and phase3-consensus, and can return unchanged metadata when no spec path exists. `_exec_agent_with_contract` conditionally passes metadata based on provider support/signature and executes at its actual project root. Managed dispatch must fail on missing required capability/context instead of using these legacy fallbacks, and must bind the actual candidate paths used by each concrete executor.
- `squad_state.AUTONOMY_MODES` is guided/semi/banzai. Banzai also has default/evidence reassessment state and consensus-specific ordered repair paths. Integrity enforcement must remain outside quality-debt/autonomy exceptions and cover those real branches, not just a generic successful normal phase.
- The existing role prose must retain neutral invariants. Provider-side ID creation requires an explicit controller proposal/reservation interaction; no pool size, placeholder format, extra allocation round limit or new COMMANDER role has been selected by the current source-storage work.
- `build_spec_graph` currently reads canonical filesystem paths and combines requirements, tasks, traceability, deferrals, amendments, verified-ledger data, memory and RE topology. `render_spec_graph` already returns deterministic bytes and `write_spec_graph` publishes them inside the spec directory. Future managed publication must bind those exact graph bytes and all required inputs; merely calling the existing builder after accepting the captured spec tree would introduce an unaccounted write. A preview builder or history projection API is not selected here.
- Existing `check_identity_candidate` opens a query-only transaction and combines typed artifact checks with explicit projection, inventory and issue contexts; binding preview separately projects the proposed lifecycle within its caller transaction. These are reusable checks, not an authenticated managed publication packet or atomic completion owner. A future wrapper must not mistake a structurally valid caller-selected role/path map for full owner/dependency coverage.

No live activation, provider run, managed registration/context migration, graph/memory effect, retarget behavior or stopped-run mutation is authorized by these observations.
