# Deterministic Spec Artifact Index Design

## Problem

Echelon spec folders accumulate many machine-readable and human-readable artifacts:
`spec.md`, `tasks.md`, `plan.md`, `coverage-map.md`, `quality-gates.md`,
`progress-report.md`, build reports, diagrams, contracts, checklists, and more.
These files are useful, but their purpose is not obvious to a human reviewer who
opens a spec folder after a run.

The current README explains the workflow at a high level, but it does not answer
the local question: "Which file should I read first, what does this file mean,
who updates it, and when is it current?"

## Goals

- Generate a concise, reliable human map inside every spec folder.
- Keep generation deterministic and Python-owned, not agent-authored.
- Avoid extra LLM tokens for artifact documentation.
- Make the index useful even when some expected files are missing.
- Preserve existing artifact filenames and agent output contracts.

## Non-Goals

- Do not rename existing artifacts.
- Do not ask agents to explain their outputs in free-form prose.
- Do not add a large artifact encyclopedia to README.
- Do not block runs solely because optional artifacts are absent.

## Proposed User Experience

Each spec folder gets:

```text
specs/<id>-<slug>/ARTIFACTS.md
```

Humans open `ARTIFACTS.md` first. It contains:

1. **Start Here** — the shortest reading path for common review goals.
2. **Current State** — derived from `spec.md` frontmatter, `tasks.md`, and known reports.
3. **Artifact Table** — file, purpose, owner/phase, updated when, audience, status.
4. **Missing Expected Files** — only for files expected at the current lifecycle stage.
5. **Generated At** — timestamp and generator version.

Example "Start Here":

```markdown
## Start Here

- Want the product/feature contract? Read `spec.md`.
- Want implementation status? Read `tasks.md`, then `progress-report.md`.
- Want design/architecture? Read `plan.md`, `data-model.md`, and `contracts/`.
- Want quality/readiness? Read `quality-gates.md`, `coverage-map.md`, and `verification-summary.md`.
- Want build evidence? Read `spec-compliance-report.md`, `code-review-report.md`, and `test-quality-report.md`.
```

## Architecture

Add a deterministic artifact index generator in Python:

```text
src/echelon/artifact_index.py
```

The module owns a static registry of known artifacts. Each registry entry has:

- `path`: relative path or glob, such as `spec.md`, `contracts/`, `checklists/*`.
- `title`: human name.
- `purpose`: one sentence.
- `phase`: discovery, specification, planning, build, verification, learning, governance.
- `owner`: agent or deterministic subsystem.
- `updated_when`: lifecycle event that creates or updates it.
- `audience`: human, machine, or both.
- `required_stage`: optional lifecycle stage where missing should be reported.

The generator scans a concrete `spec_dir`, checks which registered artifacts
exist, adds unknown files under an "Unclassified Files" section, and writes a
stable Markdown document.

## Lifecycle Hooks

Generate or refresh `ARTIFACTS.md` at these points:

- After Phase A finalize, when spec authoring artifacts are collected.
- After build finalize or harness convergence, when build and verification
  reports are available.
- On manual command:

```bash
echelon artifacts <spec_id>
```

The manual command is useful for old specs and for repairing stale indexes after
manual edits.

## README Update

README should get a short section:

- "How to read a spec folder"
- Tell users to open `specs/<id>/ARTIFACTS.md` first.
- Mention `echelon artifacts <spec_id>` to regenerate it.

README should not duplicate the full artifact registry.

## Generated File Rules

- `ARTIFACTS.md` is deterministic output and may be overwritten.
- The file must include a clear header: "Generated by Echelon. Regenerate with
  `echelon artifacts <spec_id>`."
- The generator must not modify any artifact except `ARTIFACTS.md`.
- Unknown files are listed, not deleted or rewritten.
- Missing optional files are not treated as failures.

## Status Inference

The first implementation should infer only simple status:

- `present` — file or directory exists.
- `missing` — required for the current lifecycle stage but absent.
- `optional_missing` — registered but not required.
- `unclassified` — exists but not in the registry.

Lifecycle stage can be inferred conservatively:

- `phase_a` when `spec.md` and `tasks.md` exist but no build reports exist.
- `build` when any build reports exist.
- `verified` when `verification-summary.md` exists.
- `landed` when `spec.md` frontmatter status is `landed`.

If inference is uncertain, the generator should still write the index and avoid
blocking.

## Testing

Unit tests should cover:

- Registry entries render into the expected table.
- Existing files are marked `present`.
- Missing stage-required files are listed under missing expected files.
- Unknown files are listed under unclassified files.
- Manual CLI command writes `ARTIFACTS.md`.
- README mentions `ARTIFACTS.md` and `echelon artifacts <spec_id>`.

## Rollout

1. Add the generator and unit tests.
2. Add `echelon artifacts <spec_id>`.
3. Call the generator from Phase A finalize and build/harness finalize paths.
4. Update README with the short reading guide.
5. Add or update prompt-surface docs to mention that agents should not hand-author
   `ARTIFACTS.md`; Python owns it.

## Risks

- The registry can drift from real agent outputs.
  - Mitigation: add tests for known high-value artifacts and keep README brief.
- The index could become too long.
  - Mitigation: concise purpose strings and grouping by phase.
- Agents may try to edit the file.
  - Mitigation: generated-file header and prompt-surface rule.

## Naming Decision

The generated file name should be `ARTIFACTS.md`. It is visually obvious in a
directory listing and avoids conflicting with existing `00-overview.md`, which
remains the feature summary authored during WHAT.
